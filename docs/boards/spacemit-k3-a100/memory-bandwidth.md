# SpacemiT K3 / A100 各级存储带宽与延迟

统一用 **B/cycle**，频率按实测 1.79 GHz 换算。A100 的两个 4 核簇是
`8-11` 和 `12-15`，每核私有 64 KiB L1D，每簇共享 1 MiB L2。

## 1. 结论摘要

| 通路 | 单核 | 同簇 4 核 | 全 8 核 |
|---|---:|---:|---:|
| L1D → 寄存器（向量） | **60.2 B/cycle** | 56.9 | 113.0 |
| L2 → L1D（向量） | 57.3 | 55.4 | 110.6 |
| L1D → 寄存器（标量） | 9.1 | 36.4 | 72.6 |
| TCM → 寄存器 | **64.0** | 256.0 | **511.9** |
| 主存 → L2 | 9.68 | 13.9 | 15.4 |

换算成 GB/s：单核 L1D 108 GB/s，全芯片 L1D 280 GB/s，TCM 916 GB/s，
主存 31 GB/s。

三条最重要的结论：

1. **向量 load 带宽在 4 核簇内共享，标量 load 不共享。** 即使工作集完全在
   每核私有的 64 KiB L1D 内，同簇 4 核的向量 load 聚合带宽与单核相同；
   标量 load 在同样条件下按核数线性扩展。
2. **TCM 是唯一随核数严格线性扩展的读通路**，每核恒定 64 B/cycle，
   8 核合计 511.9 B/cycle，无簇内或跨簇瓶颈。见第 5 节。
3. **L1D 与 L2 的向量读带宽测不出差别**（都是 55–60 B/cycle）。L1D 只降低
   延迟（2 cycle 对 35 cycle），不提供额外带宽。

## 2. 向量 load 的簇内共享

程序：`vector_load_mt_mre.cpp`（最小复现）、`k3_bandwidth_diagnose.cpp`
（标量/m1/m8 对照）、`k3_load_sharing.cpp`（完整核组合扫描）。

### 2.1 簇内不扩展，跨簇线性

`vector_load_mt_mre.cpp`，5 次运行取中位数：

| 配置 | B/cycle | 相对单核 |
|---|---:|---:|
| 1 核 | 49.7 | 1.00x |
| 2 核 同簇（8,9 / 8,10 / 8,11） | 64.3 | 1.29x |
| 2 核 跨簇（8,12 / 8,13 / 8,14 / 8,15） | 99.6 | **1.95x** |

三种同簇组合全部落在 63.7–64.7，四种跨簇组合全部落在 94.3–100.1，分组
一致。跨簇接近完美线性，簇内不是。

### 2.2 只有向量 load 受影响

`k3_bandwidth_diagnose.cpp`，每线程独立工作集，L1D 常驻：

| kernel | 1 核 | 同簇 4 核 | 全 8 核 | 4 核扩展 |
|---|---:|---:|---:|---:|
| 标量 `ld` | 9.09 | 36.37 | 72.57 | **4.00x** |
| 向量 `vle8.v` m1 | 51.51 | 55.24 | 110.31 | 1.07x |
| 向量 `vle8.v` m8 | 56.88 | 56.60 | 113.02 | 1.00x |

标量严格 4 倍扩展，说明 L1D 本身为每核提供独立带宽；m1 和 m8 都在簇内封顶，
说明瓶颈不限于大 LMUL。L2 常驻工作集（128 KiB/线程）给出相同形状。

### 2.3 瓶颈位于向量 load 的完成侧

`k3_pmu_diagnose.cpp`，backend stall 占 cycle 比例：

| kernel | 1 核 | 同簇 4 核 |
|---|---:|---:|
| 标量 `ld` | 0.0006 | 0.0013 |
| 向量 m1 | 0.538 | 0.876 |
| 向量 m8 | 0.920 | 0.980 |

向量 kernel 的 frontend stall 恒为 0.0002–0.001，可排除取指瓶颈；
`vadd.vi`、`vfmacc.vv` 从 1 核到 8 核严格线性，可排除向量 ALU 与寄存器文件。
因此瓶颈是**簇级共享的向量 load 完成 / cache-to-vector-register 通路**。
具体是完成队列、cache bank、fill buffer 还是写回端口，未能区分。

### 2.4 簇内曲线非单调

`k3_load_sharing.cpp`，单簇聚合：

| 簇内活跃核数 | 每簇聚合 B/cycle | 相对单核 |
|---:|---:|---:|
| 1 | 58.7 | 1.00x |
| 2 | 78.9 | 1.34x |
| 3 | 48.3 | **0.82x** |
| 4 | 56.0 | 0.95x |

3 核塌到低于单核，在两种核组合、L1D 与 L2 两种工作集下稳定复现。

对软件的含义：**访存密集的向量 kernel 在一个簇里开 2 个线程即可打满，
开到 3–4 个线程没有收益。** 全芯片最佳是每簇 2 线程共 4 线程（约 157 B/cycle），
开满 8 线程只有 110–113。

## 3. L1D 峰值与 LMUL

程序：`k3_l1d_peak.cpp`。

单核峰值 **60.2 B/cycle**，是官方宣称 512 bit/cycle（64 B/cycle）的 94%。
m8 每条 load 搬 1024 B = 16 个 cache line，实测 17.00 cycle；多出的约 1 cycle
是每条向量 load 的固定开销，在 pass 长度、指令形式、地址个数、发射顺序变化下
都不变，无法摊薄。

| 指令 | 每条字节数 | cycles/load | B/cycle |
|---|---:|---:|---:|
| `vle8.v` m1 | 128 | 2.477 | 51.7 |
| `vle8.v` m2 | 256 | 4.947 | 51.8 |
| `vle8.v` m4 | 512 | 10.149 | 50.5 |
| `vle8.v` m8 | 1024 | 17.395 | 58.9 |
| `vl8re8.v` | 1024 | 17.094 | 59.9 |

m1/m2/m4 一律是每 4 个 cache line 5 个 cycle（51.2 B/cycle），只有 m8 跳出
这个规律。**要接近 64 B/cycle 必须用 LMUL = m8 或 `vl8re8.v`；LMUL ≤ m4 的
天花板是 51.2 B/cycle。**

## 4. 分层带宽与延迟

程序：`k3_path_bandwidth.cpp`（带宽）、`k3_mem_latency.cpp`（延迟）。

| 层级 | 拟合 B/cycle | 最大相对残差 |
|---|---:|---:|
| L1D → 寄存器（8–64 KiB） | 57.7 | 3.1% |
| L2 → L1D（128–768 KiB） | 60.1 | 5.5% |
| 主存 → L2（8–64 MiB） | 9.68 | 0.4% |

L2 的 60.1 受 768 KiB 那一点影响；只看 128–512 KiB 时稳定在 56.2–57.3，
与 L1D 的 55–57 重合。

延迟（指针追逐，随机置换）：

```text
L1D 命中 ：2 cycle
L2 命中  ：约 35 cycle
主存     ：277 cycle 起，随工作集增大到 375 cycle（TLB 缺失逐渐加入）
```

容量台阶出现在 32→48 KiB 和 768 KiB→1 MiB。后者与 sysfs 的 1 MiB L2 一致；
前者早于 sysfs 的 64 KiB L1D，是 4 KiB 页随机访问下的冲突缺失，顺序访问时
整个 64 KiB 都可用。

## 5. TCM → 寄存器（A100 / K3）

测试程序：`machine-benchmarks/spacemit-k3-a100/k3_tcm_bandwidth.cpp`
（`--span 3072 --samples 7`）。

实测：

| 配置 | 每线程 B/cycle | 聚合 B/cycle | 总 GB/s @1.79 GHz |
|---|---:|---:|---:|
| 1 线程（cpu8） | 57.63 | **57.63** | 103 |
| 2 线程 异簇（cpu8+12） | 57.63 | **115.25** | 206 |
| 4 线程 同簇（cpu8–11） | 57.62–57.63 | **230.48** | 413 |
| 8 线程（cpu8–15） | 57.62–57.63 | **460.93** | **825** |

同一程序的零地址运算 kernel：

| 配置 | 聚合 B/cycle | 总 GB/s @1.79 GHz |
|---|---:|---:|
| 1 / 2 异簇 / 4 同簇 / 8 线程 | 64.00 / 127.98 / 255.95 / **511.86** | 115 / 229 / 458 / **916** |

1. **每核恒定 64 B/cycle（512 bit/cycle 数据通路），1→2→4→8 线程严格线性**，
   没有簇内或跨簇的共享瓶颈。
2. **TCM 块是"核对私有"的**：每簇 1.5 MiB 由 4 个 384 KiB 块组成，每块只对
   设备树 `cpus` 属性指定的 2 个核满速；其他核读它只有 0.17 B/cycle（约
   0.3 GB/s，慢约 330 倍）。因此每个核必须读自己归属的块。
3. 单核 TCM 峰值 64.00 B/cycle 与同核 L1D 零地址运算的 57.46 B/cycle 同量级
   （略高），即 TCM 读通路不慢于 L1D。

已知限制：多个同时存在的独立 `mmap` 会触发 `/dev/tcm` 驱动缺陷（内核 Oops），
复现时必须一次 `mmap` 申请整段再切片。

## 6. 写与 copy 带宽

程序：`k3_mem_bandwidth.cpp`。绝对值比第 3、4 节的读通路测量保守，只用于
比较读/写/copy 的相对关系。

| 模式 | 每线程工作集 | 1 核 | 同簇 4 核 | 每簇 2 核共 4 核 | 8 核 |
|---|---:|---:|---:|---:|---:|
| write | 64 KiB | 26.6 | 36.7 | 42.1 | 49.7 |
| write | 64 MiB | 14.6 | 13.9 | 14.6 | 14.5 |
| copy | 64 KiB | 42.0 | 59.9 | 118.8 | 116.6 |
| copy | 64 MiB | 15.7 | 16.2 | 16.5 | 13.1 |

写的单核峰值约 **26.6 B/cycle**，只有读的一半，簇内扩展比读更差。
copy 单核 42 B/cycle（读 21 + 写 21），每簇 2 核可达 119 B/cycle。

## 7. 主存通路

程序：`k3_path_bandwidth.cpp`，每线程 64 MiB。

| 线程绑定 | 关系 | 聚合 B/cycle |
|---|---|---:|
| 8 | 单核 | 9.6 |
| 8, 9, 10, 11 | 同簇 4 核 | 13.9 |
| 8, 10, 12, 14 | 每簇 2 核 | **17.4** |
| 8–15 | 全 8 核 | 15.4 |

单个簇就能拿到全局上限的 80%，两簇同时请求提升到 17.4 B/cycle（约 31 GB/s），
继续增加请求者不再提升。主存侧写（14.6）与 copy（15.7）和读在同一量级，
说明主存通路是读写共享的总带宽上限。

这个上限只描述**从 A100 核发起**能观察到的主存带宽。未测量 X100 侧或
X100 + A100 同时请求，因此不能当作 K3 的芯片级主存带宽上限。

## 8. 已知限制

- **K3 的 cache PMU 事件不可用。** `L1-dcache-load-misses` 恒等于
  `L1-dcache-loads`（miss/line = 1.0000），即使 4 KiB 全 L1D 常驻的工作集也是
  100% miss；`LLC-*` 事件不存在；L2 相关 raw 事件 `time_running` 为 0。
  因此层级归属靠延迟台阶和工作集尺寸判断，不靠 PMU。
- 簇内向量 load 聚合带宽随核数非单调（2 核峰值，3 核塌陷），机制未定位。
- 向量 load 是真的绕过 L1D，还是经过 L1D 但供给速率受簇内资源限制，无法区分。
  可以确定的是它**没有**获得每核私有的带宽。
- 单核向量 load 结果双峰（约 49.7 与 57.5 B/cycle 两个模式），多核结果稳定在
  ±1.5%。单核数值应取多次运行的中位数。
