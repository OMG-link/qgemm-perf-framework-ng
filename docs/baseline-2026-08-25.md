# SpacemiT IME kernel performance baseline — 2026-08-25

## Scope

This baseline measures every kernel registered by commit `251a335` with the
representative llama.cpp GEMM shape:

```text
M = 480, N = 1536, K = 1536
FMA per GEMM = M * N * K = 1,132,462,080
```

Packing, activation quantization, input generation, correctness reference,
SSH transfer, and output export are outside the timed region. Total cycles are
measured with a Linux perf hardware cycle counter. Every run is pinned to CPU 0.

## Platform

```text
Host:             spacemit-k1
CPU:              Spacemit X60
Kernel:           Linux 6.6.63, riscv64
Governor:         performance
Current/max freq: 1.6 GHz / 1.6 GHz
Compiler:         custom Clang 23.0.0git, commit bfe57bf4
Architecture:     rv64gcv_zvfh_zicbop_zba_xsmtvdot
```

The executable was built in CMake `Release` mode with fixed 256-bit vector
length compiler settings.

## Correctness preflight

Before the large performance run, all kernels were checked at
`M=80, N=160, K=320` against the locally maintained llama.cpp Q4_0 × Q8_0
scalar reference:

```text
maximum absolute error: 3.8147e-06
all kernels: PASS
```

The large shape was then run with `--no-verify` to exclude a costly scalar
reference pass from the baseline session.

## Method

Two serial rounds were executed to expose ordering and thermal variation:

1. `llama-dispatch`, `m4-batch-reduction`, `m8-batch-reduction`
2. `m8-batch-reduction`, `m4-batch-reduction`, `llama-dispatch`

Each kernel used:

```text
warmup iterations: 3
samples:           10
GEMMs per sample:  3
```

The representative value below is the midpoint of the two round medians. Raw
medians and minimums are retained in the following section.

## Summary

| Kernel | Representative cycles | Time at 1.6 GHz | FMA/cycle | Peak utilization | Relative to best |
|---|---:|---:|---:|---:|---:|
| `llama-dispatch` | 168,182,230 | 105.11 ms | 6.734 | 5.26% | 1.000× |
| `m8-batch-reduction` | 171,559,421 | 107.22 ms | 6.601 | 5.16% | 1.020× slower |
| `m4-batch-reduction` | 184,728,083 | 115.46 ms | 6.130 | 4.79% | 1.098× slower |

`FMA/cycle` is defined as `M*N*K/cycles`. Peak utilization uses the existing
project peak of 128 FMA/cycle. In FLOP terms, multiply FMA throughput by two.
At 1.6 GHz the representative throughputs are approximately 10.77, 10.56, and
9.81 GFMA/s respectively.

## Raw serial results

### Round 1 — forward order

| Kernel | Minimum cycles | Median cycles | FMA/cycle | Utilization |
|---|---:|---:|---:|---:|
| `llama-dispatch` | 167,488,223 | 168,608,091 | 6.7165 | 5.25% |
| `m4-batch-reduction` | 187,652,948 | 188,582,242 | 6.0051 | 4.69% |
| `m8-batch-reduction` | 173,072,098 | 174,028,697 | 6.5073 | 5.08% |

### Round 2 — reverse order

| Kernel | Minimum cycles | Median cycles | FMA/cycle | Utilization |
|---|---:|---:|---:|---:|
| `m8-batch-reduction` | 168,888,975 | 169,090,145 | 6.6974 | 5.23% |
| `m4-batch-reduction` | 180,567,868 | 180,873,924 | 6.2611 | 4.89% |
| `llama-dispatch` | 167,603,463 | 167,756,368 | 6.7506 | 5.27% |

The two median values differ by approximately 0.51% for `llama-dispatch`,
2.88% for `m8-batch-reduction`, and 4.17% for `m4-batch-reduction`. Future
optimization comparisons should account for this observed run-to-run spread.

## Selected-cycle instrumentation

This historical baseline was recorded while `llama-dispatch` temporarily
instrumented `SQ4BIT_KERNEL_COMP_4x16x16`. Its two median selected-region
measurements were 25,893,586 and 25,962,643 cycles, averaging about 15.42% of
total cycles. The insertion point was removed after this baseline; the reusable
`selected_cycles` tools remain available. Future no-instrumentation performance
comparisons should establish a fresh baseline rather than attributing a small
difference solely to a kernel optimization.

## Reproduction

Build and run the correctness preflight:

```bash
./compile-and-test.sh build
./compile-and-test.sh run \
  --kernel all --m 80 --n 160 --k 320 \
  --warmup 3 --samples 3 --iterations 3
```

Performance round 1:

```bash
./compile-and-test.sh run \
  --kernel all --m 480 --n 1536 --k 1536 \
  --warmup 3 --samples 10 --iterations 3 --no-verify
```

Performance round 2 should be run serially in reverse order:

```bash
./compile-and-test.sh run \
  --kernel m8-batch-reduction --m 480 --n 1536 --k 1536 \
  --warmup 3 --samples 10 --iterations 3 --no-verify
./compile-and-test.sh run \
  --kernel m4-batch-reduction --m 480 --n 1536 --k 1536 \
  --warmup 3 --samples 10 --iterations 3 --no-verify
./compile-and-test.sh run \
  --kernel llama-dispatch --m 480 --n 1536 --k 1536 \
  --warmup 3 --samples 10 --iterations 3 --no-verify
```

Do not launch baseline rounds concurrently: all remote invocations are pinned
to CPU 0 and would otherwise compete for the same core.
